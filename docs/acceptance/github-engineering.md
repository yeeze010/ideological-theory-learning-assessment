# Git/GitHub 工程规范

## 分支模型

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 生产稳定版本 | 仅接受通过验收的 release 合并 |
| `develop` | 日常集成 | 功能分支合并目标 |
| `feature/*` | 功能开发 | 关联需求或 Issue |
| `fix/*` | 缺陷修复 | 关联缺陷单与回归用例 |
| `release/*` | 发布候选 | 只接受阻断缺陷修复 |

## 提交与 PR

- Commit 建议采用 Conventional Commits：`feat:`、`fix:`、`docs:`、`test:`、`refactor:`、`chore:`。
- PR 必须包含需求背景、实现说明、测试结果、截图或录屏、风险说明。
- 影响数据库结构时必须包含迁移脚本、回滚说明和测试数据策略。
- 影响权限、考试、成绩、积分、证书的 PR 需要至少 2 人 Review。

## CI 建议

| 阶段 | 检查项 |
|---|---|
| install | 锁文件一致性、依赖安装 |
| lint | ESLint、Prettier、类型检查 |
| test | 单元测试、接口测试、共享包测试 |
| build | 前端构建、后端构建 |
| e2e | 核心学习考试流程 |
| artifact | Docker 镜像、部署包、文档包 |

## Issue 与验收闭环

每个功能模块建立 Issue，包含验收标准和测试用例链接。缺陷单必须包含复现步骤、期望结果、实际结果、环境、截图或日志。里程碑关闭前确认所有阻断缺陷关闭，非阻断缺陷进入后续版本。

## GitHub 能力使用建议

项目接入 GitHub 后，可使用 PR 评论处理、CI 修复、Review 线程跟踪和变更文件审查能力辅助开发。典型动作包括定位失败 CI、根据 Review 修改代码、补充测试、生成发布说明和验收清单。
